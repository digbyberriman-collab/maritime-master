# Phase 2 — Cross-module workflow / business-logic correctness

Scope: status/state-machine lifecycles outside the ISM forms signature workflow (already fixed in migrations
`20260919210000`/`20260919220000` — not re-audited here). For every module below the test applied is the one in
the brief: *can an authenticated user with database access set this record to an invalid/out-of-order status by
calling `supabase.from(...).update()` directly, bypassing whatever the UI intends?*

Method: grepped `supabase/migrations/**` for each table's `CREATE TABLE` (status column + `CHECK`), its
`CREATE POLICY ... FOR UPDATE` (looking for a `WITH CHECK` that pins role/transition, the way the ISM forms fix
does), and any trigger; then grepped `src/modules/**` for the client mutations that touch that table, and for
whether the matching edge function (if any) is actually called from the client.

### [WORKFLOW] — Crew member can flip their own employment `status` back to Active after being deactivated
Severity: Critical
Location: `supabase/migrations/20260125143210_72ec62e6-2afe-42e8-9ebf-d871d1dc44f7.sql:73` (policy `"Users can update their own profile"`, `USING (user_id = auth.uid())`, no `WITH CHECK`, never dropped/superseded) + `supabase/migrations/20260125160927_7551738f-f9ed-461c-9ee5-da3933344eb6.sql:70` (`profiles.status text DEFAULT 'Active'`, no `CHECK`) + `supabase/migrations/20260917190000_hris_review_fixes.sql:114-136` (`profiles_guard_privileged_columns` trigger); client: `src/modules/crew/hooks/useCrew.ts:571-620` (`deactivateCrew`)
Description: Postgres RLS combines multiple permissive policies for the same command with `OR`. The original, never-revoked `"Users can update their own profile"` policy lets any user update **every column** of their own `profiles` row with no `WITH CHECK`. A later migration added a `BEFORE UPDATE` trigger (`profiles_guard_privileged_columns`) that blocks self-edits to `role`, `account_status`, `company_id` and `user_id` for non-HR-admins — but it does **not** cover `status` (the field `deactivateCrew` sets to `'Inactive'`) or `employment_status`. `profiles.status` also has no `CHECK` constraint (unlike, e.g., `crew_contracts.status`), so any string is accepted.
Impact: HR marks a crew member `Inactive` via the roster's "Deactivate" action (`useCrew.ts` `deactivateCrew`). The affected user's own session can immediately call `supabase.from('profiles').update({ status: 'Active' }).eq('user_id', <self>)` and reappear as Active in the crew roster, `useCrewCount` (used on dashboards), and anywhere else that filters `profiles.status = 'Active'` — fully undoing an HR deactivation with a single unauthenticated-by-role client call. Because there's no `CHECK`, the same call can also set `status` to any garbage string, silently breaking every UI filter/badge keyed on `'Active'`/`'Inactive'`.
Suggested fix: Add `status` (and `employment_status`) to the `profiles_guard_privileged_columns` trigger's guarded-column list (or fold them into a single, explicit allow-list of self-editable columns rather than a deny-list), and add `CHECK (status IN ('Active','Inactive', ...))` to `profiles.status`.

### [WORKFLOW] — Crew termination has no server-side cascade: payroll, certificates and work-rest records are left dangling, and three unsynced "status" columns disagree with each other
Severity: High
Location: `src/modules/crew/hooks/useCrew.ts:569-599` (`deactivateCrew`); `supabase/migrations/20260125160927_7551738f-f9ed-461c-9ee5-da3933344eb6.sql:70` (`profiles.status`); `supabase/migrations/20260501100000_work_rest_module.sql:11` (`profiles.employment_status`, added later, independent column); `supabase/migrations/20260129122422_b6a602fd-bb36-4f62-a097-ea95ee26fa71.sql:68` (`profiles.account_status`)
Description: `profiles` carries three independent, string-typed "is this person still here" columns that were added in three separate migrations and are never kept in sync by any trigger: `status` (`'Active'/'Inactive'`, used by the crew roster/dashboard count), `employment_status` (free text, edited from the HR "Personal Details" form, read by the work-rest module to decide whose hours to track), and `account_status` (`'active'/'disabled'/'invited'/'not_invited'`, gates login). `deactivateCrew` only writes `status` and ends the current `crew_assignments` row (`is_current=false`); it never touches `employment_status` or `account_status`, and there is no trigger or RPC that cascades a termination into `crew_contracts` (status stays whatever it was — not `'terminated'`), `certificates`/crew certificate records (keep counting toward expiry alerts for someone no longer employed), open `payroll` runs/lines, or work-rest hour-of-rest obligations.
Impact: Deactivating a crew member through the roster UI leaves them fully logged-in-capable (`account_status` untouched), still "on watch" for work-rest compliance tracking, still generating certificate-expiry alerts, and with contracts that never move to `'terminated'` — none of the systems that are supposed to close out on termination actually do, because each reads a different one of the three status columns.
Suggested fix: Pick one authoritative lifecycle column (or an enum) and drive it from a single server-side function (e.g. `terminate_crew_member(profile_id, reason, effective_date)` as a `SECURITY DEFINER` RPC) that atomically sets `status`, `employment_status`, `account_status`, closes the active `crew_assignments` row, transitions the active `crew_contracts` row to `'terminated'` with `terminated_at`/`termination_reason`, and leaves certificate/payroll records untouched only if that is the intended business rule (currently it looks accidental, not intended).

### [WORKFLOW] — Incident and CAPA closure is entirely client-enforced; any company member can close/self-verify a corrective action
Severity: Critical
Location: `supabase/migrations/20260125220549_d85c9e1e-a6aa-413c-a0a5-09dafd5a0c67.sql:85-108` (`"Users can update incidents/corrective actions in their company"`, `USING (user_belongs_to_company(...))`, no `WITH CHECK`, no role check); client: `src/modules/incidents/hooks/useCorrectiveActions.ts:254-302` (`useVerifyCAPAction`), `:143-176` (`useUpdateCorrectedAction`, generic `.update(updateData)`); `src/modules/incidents/hooks/useInvestigation.ts:159-191` (`useUpdateInvestigation`, generic `.update(updateData)`)
Description: `incidents.status`, `incidents.investigation_status` and `corrective_actions.status` do have vocabulary `CHECK` constraints (unlike most other modules audited here), but the `UPDATE` RLS policy on `incidents` and `corrective_actions` only checks company membership — there is no role gate and no `WITH CHECK` restricting *which* status transitions are legal or *who* may make them. `useUpdateCorrectedAction` and `useUpdateInvestigation` both accept an arbitrary partial payload and forward it straight to `.update()`. `useVerifyCAPAction` sets `verified_by: user?.id` from whatever user happens to call it — there is nothing stopping the person who performed the corrective action (`assigned_to`) from also being the one who calls verify-and-close on themselves, and nothing stopping any company member (not just DPA/investigator) from skipping straight from `'Open'` to `'Closed'`, or an incident from being set to `'Closed'` while its `investigation_status` is still `'Not Started'`.
Impact: ISM Code CAPA closure is supposed to have independent verification; here any authenticated company member can `supabase.from('corrective_actions').update({ status: 'Closed', verified_by: <self>, verified_date: today }).eq('id', anyId)` — self-verifying and closing their own corrective action, or closing out a safety incident without ever running an investigation. This is the same class of bug the ISM-forms fix addressed (client-assumed workflow, no DB-side transition guard), just in a module that wasn't in scope for that earlier fix.
Suggested fix: Add a `WITH CHECK` (or `BEFORE UPDATE` trigger, following the pattern now used for `legal_requests` in `20260919120000_legal_module.sql`) that (a) restricts `status`/`verified_by`/`investigation_status` changes to users with an incidents/DPA role, (b) rejects `corrective_actions.status = 'Closed'` unless `verified_by <> assigned_to` and the record passed through `'Verification'` first, and (c) rejects `incidents.status = 'Closed'` unless `investigation_status = 'Completed'` when `investigation_required = true`.

### [WORKFLOW] — Certificate DPA-approval step is completely bypassable: the DPA-gated edge function is dead code, the real UI path writes `status` directly with no role check
Severity: Critical
Location: `supabase/functions/review-certificate/index.ts:43-46` (server-side `if (profile.role !== 'dpa') throw ...`); `supabase/migrations/20260125222557_29f42436-486d-4b9e-bb76-2aab337091b8.sql:16` (`certificates.status`, comment-only, **no `CHECK`**), `:50-52` (`"Users can update certificates in their company"`, `USING (user_belongs_to_company(...))`, no role restriction, no `WITH CHECK`); client: `src/modules/certificates/hooks/useCertificates.ts:198-210` (`updateCertificate`, sets `status` via `calculateCertificateStatus()` on any update), `:230-278` (`renewCertificate`, directly inserts the renewal + supersedes the old cert — no role check)
Description: `review-certificate` is a well-built edge function that correctly enforces "only DPA can approve/reject/renew" server-side using the service-role client (bypassing RLS to do so, which is fine since it re-checks the role itself). However, `grep -rn "review-certificate" src/` finds **zero** references anywhere in the client — it is never called. The actual UI flow (`useCertificates.ts`, wired into `AddCertificateModal`/`CertificateDetailModal`/the certificates pages) performs its own `renewCertificate` and `updateCertificate` mutations that write `certificates.status` directly via `supabase.from('certificates').update(...)`, with no role check of any kind, and the table's RLS `UPDATE` policy imposes none either (any company member passes `user_belongs_to_company`). `certificates.status` also has no `CHECK` constraint, so any string is accepted.
Impact: The DPA-approval control this module was clearly designed around (per `review-certificate`'s own logic and the checklist's premise) does not exist in practice for any certificate touched through the real UI: any authenticated company member — crew, purser, anyone — can renew, "approve" (set `status: 'Valid'`), or supersede any vessel/crew certificate without any DPA sign-off, by calling the same `updateCertificate`/`renewCertificate` mutations the UI itself uses, or an equivalent raw `.update()`.
Suggested fix: Either (a) route `updateCertificate`/`renewCertificate` through the `review-certificate` edge function so the DPA check is actually exercised, or (b) if the team decides certificate self-service renewal is intended, add a `WITH CHECK` clause to the `certificates` UPDATE policy that requires DPA role for `status` transitions into `'Valid'`/`'Superseded'`/`'Rejected'`, and add a `CHECK (status IN ('Valid','Expiring_Soon','Expired','Suspended','Superseded','Rejected'))` constraint. Either way, decide which of the two parallel code paths is authoritative and remove the other.

### [WORKFLOW] — Drill completion and audit/CAPA-finding status are unrestricted client writes; the role-gated `complete-drill` edge function is dead code
Severity: High
Location: `supabase/functions/complete-drill/index.ts:69-73` (server-side role check: `dpa`/`master`/`shore_management` only) and `:87-90` (guards against re-completing a `'Completed'` drill); `supabase/migrations/20260125224405_aaa3b17d-e065-4210-9a9c-2d96fe1db9fc.sql:25` (`drills.status`, comment-only, **no `CHECK`**), `:138-140` (`"Users can update drills in their company"`, company-membership only, no role/`WITH CHECK`); `supabase/migrations/20260125223322_9cb6b943-ed2e-4d27-866f-431f3651f4c9.sql:16` (`audits.status`), `:36` (`audit_findings.status`), `:59` (`management_reviews.status`) — none have `CHECK`, and `:77-81`/`:102-104`/`:127-129` give the same open, role-free `UPDATE` policy; client: `src/modules/drills/hooks/useDrills.ts:213-232` (`updateDrillMutation`, generic `.update(updates)` accepting any `Partial<Drill>` including `status`)
Description: Same pattern as certificates. `complete-drill` correctly role-gates who can mark a drill `'Completed'` and atomically records participants/evaluations/deficiencies (and auto-opens a CAPA for major/critical deficiencies) — but `grep -rn "complete-drill" src/` finds no caller; it is unused. The generic `updateDrillMutation` in `useDrills.ts` is the only drill-status write path actually reachable from the UI, and it lets any company member set `status` (or any other column) to anything, including `'Completed'`, without recording any of the participant/evaluation/deficiency data the edge function considers part of "completing" a drill. `audits`, `audit_findings` and `management_reviews` have the identical shape: free-text `status` with a code comment listing the intended vocabulary but no `CHECK`, and an `UPDATE` policy scoped only to company membership.
Impact: A drill can be marked `'Completed'` with zero evidence it happened (no participants, no evaluation, no deficiency capture, no auto-CAPA for a defective muster), by any crew member, not just DPA/master/shore management. Audit findings (`audit_findings.status`) can jump straight from `'Open'` to `'Closed'` without ever having a CAPA assigned or being reviewed, and any string at all is accepted for `audits.status`/`audit_findings.status`/`management_reviews.status` since there's no vocabulary `CHECK`.
Suggested fix: Wire the drill-completion UI to call `complete-drill` instead of `updateDrillMutation` for the status transition (keep the generic mutation for non-status fields, or strip `status` out of its payload type). Add `CHECK` constraints for `drills.status`, `audits.status`, `audit_findings.status`, `management_reviews.status` matching their documented vocabularies, and add a role-scoped `WITH CHECK` (or trigger) to each `UPDATE` policy so only intended roles (DPA/master/shore management/lead auditor) can transition status.

### [WORKFLOW] — `crew_contracts` termination is role-gated but not transition-guarded (informational / lower severity)
Severity: Medium
Location: `supabase/migrations/20260917110000_hris_phase1_employee_records.sql:108-110` (`status text ... CHECK (status IN ('draft','active','expired','terminated','superseded'))`), `:145-152` (`"crew_contracts_update"` policy: `USING/WITH CHECK (user_belongs_to_company(...) AND hr_can_edit(...))`); client: `src/modules/hris/components/contracts/TerminateContractDialog.tsx` (UI asks for `terminated_at` + `reason`), `src/modules/hris/lib/contractHelpers.ts:296-300` (`ContractWritePayload` explicitly omits `terminated_at`/`termination_reason` from the generic form payload — a good sign someone thought about this)
Description: Unlike the other tables above, `crew_contracts.status` **does** have a vocabulary `CHECK`, and its `UPDATE` policy **does** require `hr_can_edit()` (fleet_master/captain/purser/DPA/shore_management/superadmin) — this is close to correct. What is still missing is any state-machine guard: nothing stops an HR-privileged caller from writing `status: 'terminated'` directly (skipping `TerminateContractDialog`, so `terminated_at`/`termination_reason` stay null), or from writing `status: 'active'` over a `'terminated'`/`'superseded'` row (un-terminating a contract), or `'terminated'` directly from `'draft'` without ever passing through `'active'`.
Impact: Lower severity than the other findings because the actor must already hold an HR-ish role, but it means the audit trail for "why/when was this contract ended" is optional rather than enforced, and a resurrected `'terminated'` → `'active'` contract would silently re-trigger the `crew_contracts_after_write` trigger's "supersede any other active contract" logic in a way nobody intended.
Suggested fix: Add a `BEFORE UPDATE` trigger that (a) requires `terminated_at` and `termination_reason` to be set together with any transition into `'terminated'`, and (b) rejects transitions out of `'terminated'`/`'superseded'`/`'expired'` back into `'active'`/`'draft'`.
