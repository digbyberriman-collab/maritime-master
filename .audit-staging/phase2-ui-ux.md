### [UI-UX] — Dark mode is never applied on load; the platform effectively ships light-mode-only despite "dark-mode-first" intent
Severity: Critical
Location: `src/modules/settings/components/sections/AppearanceSection.tsx:58-83` (`loadAppearanceSettings`) and `:104-135` (`applyTheme` / `handleSave`); `src/index.css:6-9` (`:root` light values) vs `src/index.css` `.dark` block; `tailwind.config.ts:5` (`darkMode: ["class"]`); `src/App.tsx` (no theme bootstrap)
Description: `tailwind.config.ts` uses class-based dark mode (`darkMode: ["class"]`), and `src/index.css` defines a complete, well-formed `.dark` variable set. The only code anywhere in the repo that ever toggles the `dark` class on `document.documentElement` is `applyTheme()` inside `AppearanceSection.tsx` — and it is called from exactly one place: the end of `handleSave()`, i.e. only when the user is on Settings → Appearance and clicks Save. `loadAppearanceSettings()` (called on mount) fetches the user's saved `theme` value from `user_preferences` into component state but never calls `applyTheme()` with it. A repo-wide search confirms there is no `ThemeProvider`, no `next-themes` usage, no `prefers-color-scheme` check, and no other `classList`/`documentElement` reference anywhere else in `src/`. `App.tsx`'s root component tree (`QueryClientProvider` → `TooltipProvider` → `BrowserRouter` → `AuthProvider` → `BrandingProvider` → `VesselProvider` → `ErrorBoundary` → `AppRoutes`) has no theme bootstrap step.
Impact: On every fresh page load or hard refresh, the app renders with the light-mode CSS variables (`--background: 210 20% 98%`, near-white) regardless of what a user previously saved as their theme preference. A user who sets "Dark" in Settings sees it apply only transiently, in-memory, for the remainder of that same browser session tab — the moment they reload, open a new tab, or return the next day, they are back in light mode with no indication anything reverted. For a platform whose stated design intent is dark-mode-first (crew working at night, on the bridge, or in low-light environments), the dark theme is effectively non-functional as shipped, not "a bit inconsistent."
Suggested fix: Add a boot-time effect (in `App.tsx` or a small `ThemeProvider`) that reads the user's saved `theme` (from `user_preferences`, or `localStorage` as a synchronous first-paint fallback to avoid a flash of the wrong theme) and calls the same `classList.toggle('dark', …)` logic before/on first render, then re-run it whenever the preference changes elsewhere. Consider adopting `next-themes` (already implied by the shadcn `sonner.tsx` boilerplate) to get this for free, including `prefers-color-scheme` handling and no-flash SSR-safe boot.

### [UI-UX] — Status/type badge colors are hardcoded to the light Tailwind palette with no dark-mode variant
Severity: High
Location: `src/modules/crew/pages/admin/TravelRecordsPage.tsx:37-52` (`statusColors`, `typeColors` maps: `bg-gray-100 text-gray-700`, `bg-blue-100 text-blue-700`, `bg-green-100 text-green-700`, `bg-yellow-100 text-yellow-700`, `bg-red-100 text-red-700`, `bg-orange-100 text-orange-700`, `bg-purple-100 text-purple-700`, `bg-emerald-100 text-emerald-700`); `src/modules/vessels/pages/CompanyDetails.tsx:135`; `src/modules/ism/pages/InvestigationsPage.tsx:73-76`; `src/modules/crew/pages/admin/PreDepartureDetailPage.tsx:335`
Description: 35 files in `src/modules` use literal Tailwind gray/color-shade classes (`bg-gray-*`, `text-gray-*`, `border-gray-*`) for status badges and UI chrome. Only 2 of those 35 pair any of these with a `dark:` sibling class; the rest have none. This is the opposite pattern from the correct usage seen elsewhere in the same codebase (e.g. `Vessels.tsx:178` uses the semantic token pattern `bg-success/20 text-success border-success/30`, which adapts automatically via the CSS variables). The `-100`/`-700` pastel combinations in `TravelRecordsPage.tsx` are the clearest case: an entire status/type badge palette for crew travel records, built entirely from fixed light-mode Tailwind shades.
Impact: Once dark mode is actually wired up (see prior finding), every one of these badges will render as a light pastel pill (near-white background, dark text) sitting on a dark page background — jarring, low-contrast in places, and visibly inconsistent with the rest of the UI's theme-aware badges (`Badge` variants, `bg-success/20`-style tokens) sitting right next to them in other modules.
Suggested fix: Replace literal `bg-{color}-100 text-{color}-700` pairs with the app's existing semantic tokens (`bg-success/20 text-success`, `bg-warning/20 text-warning`, `bg-critical/20 text-critical`, `bg-muted text-muted-foreground`, etc.), or at minimum add matching `dark:bg-{color}-900/30 dark:text-{color}-300` variants everywhere the light-only classes are used today.

### [UI-UX] — Query errors are silently indistinguishable from "no data" in ~30 of 34 modules; no global error surface exists
Severity: High
Location: `src/App.tsx:16-26` (`QueryClient` has no `queryCache.onError`); confirmed absent in `src/modules/vessels/pages/Vessels.tsx`, `src/modules/incidents/pages/Incidents.tsx`, `src/modules/documents/pages/Documents.tsx`, and all of `ism`, `legal`, `crew`, `new-build`, `maintenance`, `logbooks`, `training`, `certificates`, `risk-assessments`, `drills`, `audits`, `itinerary`, `work-rest`, `rotation-planner` (0 files in any of these 14 modules reference `isError`)
Description: Repo-wide, only `hris` and `health` (plus `notifications` and `help`) ever check TanStack Query's `isError`/render a distinct error UI. In every sampled page across Vessels, Incidents, Documents, ISM, Legal, Crew, New Build, Maintenance, Logbooks, Training, Certificates, Risk Assessments, Drills, Audits, Itinerary and Rotation Planner, the pattern is uniformly `isLoading ? <Skeleton/> : data.length === 0 ? <EmptyState/> : <Table/>` — there is no third branch for a failed fetch. The `QueryClient` in `App.tsx` also sets no `queryCache: { onError }`, so there is no app-wide fallback toast either.
Impact: If a query fails for any reason (network drop at sea, a timeout, or an RLS policy silently denying a `SELECT`), the page renders the exact same "No vessels added yet" / "No incidents reported" / "No documents found" empty state as a genuinely empty table. A user has no way to tell "there's nothing here" from "the fetch just failed" — in a fleet-safety/compliance context (incidents, drills, risk assessments, audits), this is a materially misleading failure mode, not just a cosmetic gap. It also means any RLS misconfiguration (several are flagged elsewhere in this audit) fails silently in the UI rather than surfacing to the user or support.
Suggested fix: Either add a `queryCache: { onError }` handler on the shared `QueryClient` that fires a destructive toast on any query failure app-wide, or (better, since some errors are page-contextual) add a third `isError` branch alongside every existing `isLoading`/empty check, matching the pattern already used correctly in `hris` (e.g. `DisciplinaryOverview.tsx`, `OnboardingOverview.tsx`) and `health`.

### [UI-UX] — RBAC department-scope save has zero user feedback on failure
Severity: High
Location: `src/modules/users-access/hooks/useDepartmentScope.ts:24-49` (`useSaveDepartmentScope`, no `onError`); `src/modules/users-access/pages/UsersAccessDetailPage.tsx:124-127` (`handleDeptChange` calls `saveDept.mutate({...})` with no options object at all)
Description: Every other mutation on this same page (`applyPreset`, `saveOverride`) is called with an explicit `{ onSuccess, onError }` pair that fires a `toast`. `handleDeptChange` — which saves a user's department-scope restriction, an access-control-relevant setting — calls `saveDept.mutate({ userId, departments: next })` with no second argument, and the underlying hook itself defines no `onError` either (only `onSuccess: (_d, vars) => qc.invalidateQueries(...)`).
Impact: If the underlying `delete`+`insert` against `user_permission_overrides` fails (RLS denial, network error, constraint violation), the admin gets no toast, no error, nothing — the UI looks exactly as if the save succeeded. On an access-control admin surface, a silently-failed permission change is a real operational risk (an admin believes they restricted or granted access and did not).
Suggested fix: Add the same `{ onSuccess: () => toast(...), onError: (e) => toast({ variant: 'destructive', ... }) }` pattern used by the other three handlers on this page (`handlePresetChange`, `handleModuleChange`, `handleSetAll`) to `handleDeptChange`, and add a matching `onError` to `useSaveDepartmentScope` itself as a safety net.

### [UI-UX] — Itinerary entry create/update/delete mutations give no success or failure feedback anywhere
Severity: Medium-High
Location: `src/modules/itinerary/hooks/useItinerary.ts:101-218` (`useCreateEntry`, `useUpdateEntry`, `useUpdateEntryVessels`, `useDeleteEntry` — all four have only `onSuccess: () => queryClient.invalidateQueries(...)`, no `onError`, no `toast` import at all in this file); call sites `src/modules/itinerary/components/EntryDetailPanel.tsx` and `src/modules/itinerary/pages/PostponedEntriesPage.tsx` also do not add their own toasts around these calls
Description: Unlike the sibling hook in the same module (`useTripSuggestions.ts`, which correctly pairs every mutation with `toast({...})` on both success and error), `useItinerary.ts` has zero `toast` usage. Creating a trip, editing one, changing which vessels it's linked to, or deleting it all resolve or reject with no visible confirmation.
Impact: A trip/itinerary edit that fails (e.g. a vessel-link write failing partway through the three sequential Supabase calls in `useUpdateEntryVessels`) leaves the UI showing stale data with no error shown, and a successful save gives no positive confirmation either — a user cannot tell whether their edit "took."
Suggested fix: Add `onSuccess`/`onError` toast pairs to all four mutations in `useItinerary.ts`, matching the pattern already used correctly in `useTripSuggestions.ts` in the same module.

### [UI-UX] — Logbooks module: 3 of 4 mutation hook files have no toast feedback at all
Severity: High
Location: `src/modules/logbooks/hooks/useLogbookSamples.ts`, `src/modules/logbooks/hooks/useLogbookWorkspace.ts`, `src/modules/logbooks/hooks/useLogbookRegistry.ts` (0 `toast` references in any of the three); contrast with `src/modules/logbooks/hooks/useLogbookAttachments.ts` (6 `toast` references, correctly done)
Description: Official ship's logbooks are a compliance/legal-recordkeeping feature (per `SITE_MAP.md`, 9 dedicated DB tables). ### [UI-UX] — Destructive-delete confirmation is split between the shared `AlertDialog` component and the native, unstyled `window.confirm()`
Severity: Medium
Location: `src/modules/logbooks/pages/LogbookWorkspace.tsx:301`; `src/modules/crew/components/FullCrewEditModal.tsx:259`; `src/modules/crew/pages/admin/TravelRecordDetail.tsx:168`; `src/modules/new-build/pages/DeckPlan.tsx:509`; `src/modules/new-build/pages/interior/InteriorMaterials.tsx:1432`; `src/modules/new-build/pages/PurchaseOrders.tsx:251`; `src/modules/new-build/pages/Piping.tsx:779`; `src/modules/ism/forms/pages/FormSchedules.tsx:142`; `src/modules/ism/forms/pages/DraftTemplates.tsx:84`; `src/modules/itinerary/components/EntryDetailPanel.tsx:147`
Description: 10 delete-confirmation call sites across Logbooks, Crew, New Build, ISM Forms and Itinerary use the browser's native `confirm()`/`window.confirm()` dialog, while 40+ other delete sites across the same and other modules (Vessels, Documents, Certificates, HRIS, Legal, Health, Maintenance, Risk Assessments) use the shared shadcn `AlertDialog` component. Notably, `itinerary`'s own `EntryDetailPanel.tsx:147` uses `confirm()` for deleting an itinerary entry, while `PostponedEntriesPage.tsx` in the very same module deletes the same kind of record via a proper `AlertDialog`, i.e. the same underlying action has two different confirmation UIs depending which screen you delete it from.
Impact: The native `confirm()` dialog is unstyled system chrome that ignores the app's theme entirely (it will show a light OS dialog even in dark mode once that's fixed), blocks the JS event loop, cannot show a loading/pending state during the async delete, and reads as visually "broken" compared to the rest of the app's polished dialogs.
Suggested fix: Replace all 10 `confirm()`/`window.confirm()` call sites with the shared `AlertDialog` component, following the pattern already used in `DeleteVesselDialog.tsx` / `DeleteDocumentDialog.tsx`.

### [UI-UX] — Rotation Planner deletes fire immediately with no confirmation of any kind
Severity: Medium
Location: `src/modules/rotation-planner/pages/RotationPlannerPage.tsx:284-288` (`onDeleteSelection`), `:366-371` (Delete/Backspace keyboard shortcut calls `onDeleteSelection()` directly), `:523` (`onDelete={(id) => void applyDeletes([id], 'Delete block')}`); `src/modules/rotation-planner/components/Toolbar.tsx:170-171`; `src/modules/rotation-planner/components/BlockDetailDrawer.tsx:140`
Description: Unlike every other destructive-delete site sampled in this audit (all of which use either `AlertDialog` or, at minimum, `window.confirm()`), the Rotation Planner's block delete — reachable via a toolbar button, a detail-drawer button, and a global `Delete`/`Backspace` keyboard shortcut while any block is selected — calls `applyDeletes(...)` directly with zero confirmation step. This is mitigated by an undo/redo stack (`onUndo`/`onRedo`) that the page also implements, but the deletion itself is still silent and instant.
Impact: A crew rotation block (representing a real onboard/leave assignment) can be deleted by a single keystroke while multiple blocks are selected, with no "are you sure" — a data-loss vector that is inconsistent with the confirm-then-delete pattern used everywhere else in the app for records of comparable importance (vessels, documents, crew certificates).
Suggested fix: At minimum, gate the keyboard-shortcut bulk-delete path (and the multi-select toolbar delete) behind a lightweight `AlertDialog` when more than one block is selected; the single-block delete-from-drawer path could reasonably rely on the existing undo stack if a toast confirming "Deleted — Undo" is added alongside it (currently there is no such toast either, see prior findings on toast consistency).

### [UI-UX] — ~20% of sampled real (non-placeholder) pages have zero responsive breakpoint classes
Severity: Medium
Location: 52 of 257 files under `src/modules/*/pages/*.tsx` contain no `sm:`/`md:`/`lg:`/`xl:` Tailwind classes at all, including substantial, real pages such as `src/modules/rotation-planner/pages/RotationPlannerPage.tsx` (546 lines), `src/modules/crew/pages/LeavePlannerPage.tsx` (682 lines), `src/modules/documents/pages/ReviewQueue.tsx` (281 lines), `src/modules/dashboard/pages/DPADashboard.tsx` (176 lines), `src/modules/hris/pages/CompensationSettingsPage.tsx` (274 lines), `src/modules/itinerary/pages/FleetTimelinePage.tsx`, `src/modules/crew/pages/LeaveRequestsPage.tsx`; `src/shared/hooks/use-mobile.tsx` (the app's only mobile-detection hook) is imported in just 2 files repo-wide
Description: `DashboardLayout`/`SidebarNavigation` itself is a well-built responsive baseline (off-canvas mobile drawer with overlay, focus handling, Escape-to-close, `lg:` breakpoint for desktop-static sidebar) — that part is solid and consistent. But a meaningful fraction of the actual page content rendered inside that shell has no responsive handling of its own: fixed-width grids, multi-column toolbars, and drag-and-drop/canvas UIs (Rotation Planner in particular) that assume a wide desktop viewport, with no `useIsMobile` fallback or stacking breakpoints.
Impact: On a tablet (portrait or landscape) — the plausible device for crew or officers using this platform at sea — these pages will either overflow, require constant horizontal scrolling, or render controls too small/cramped to use, despite this being a fleet-management SaaS product whose users are not guaranteed a desktop monitor.
Suggested fix: Prioritize responsive review for the highest-traffic desktop-only pages first (Rotation Planner, Leave Planner, dashboards), adding stacking (`flex-col md:flex-row`) and reflow rules consistent with the many other pages in the same modules that already do this (e.g. `Vessels.tsx`, `Documents.tsx` both use `flex-col sm:flex-row` for their headers).

### [UI-UX] — Sitemap "placeholder" classification is inaccurate for Health, HRIS and New Build; real pages currently work only by a fragile route-declaration-order coincidence
Severity: Medium
Location: `src/config/sitemap.ts` (`L()` helper, `:41-48`; `PLACEHOLDER_LEAVES`, `:659-673`); `src/routes/index.tsx:812-826` (`{hrisRoutes}` / `{healthRoutes}` rendered *before* `{PLACEHOLDER_LEAVES.map(...)}` in the same `<Routes>` list); `src/modules/health/paths.ts`; `src/modules/hris/paths.ts`; `src/modules/new-build/routes.tsx`
Description: This is a factual clarification of Phase 1's raw "262 placeholder routes" figure, needed so Phase 4 doesn't over- or under-prioritize by nav section. Computing placeholder leaves per top-level nav section against `NAVIGATION_ITEMS` gives: **Fleet 2/14 (14%)**, **Vessel 120/151 (79%)**, **Shoreside 8/8 (100%)**, **Health & Wellness 51/51 (100%)**, **Yard 62/62 (100%)**, **HRIS 20/26 (77%)**. Taken at face value, this makes Health, HRIS and Yard look almost entirely unbuilt. Cross-referencing `PLACEHOLDER_LEAVES` paths against each module's own real, explicitly declared `<Route>` paths shows this is misleading for three of the six:
- **Health**: all 51/51 flagged-placeholder leaves have an exact-matching real route in `healthRoutes` (verified programmatically against `HEALTH_PATHS`). Because `{healthRoutes}` is rendered *before* `{PLACEHOLDER_LEAVES.map(...)}` in the same `<Routes>` array, and React Router v6 resolves ties between identically-scored static paths by original declaration order (confirmed empirically with `matchRoutes` in this repo's own `react-router-dom` version), **the real health pages currently win and render correctly** — none of these 51 actually show "Coming Soon" today.
- **HRIS**: same pattern — all 20/26 flagged leaves are shadowed by real routes in `hrisRoutes` and currently render correctly.
- **New Build** (part of the "Yard" 62/62 figure): all 24 flagged leaves are shadowed by real routes in `newBuildRoutes` and currently render correctly.
- **Refit** (the other half of "Yard"): 0 of 38 flagged leaves match any real route — these are genuinely "Coming Soon" today. This matches and confirms Phase 1's already-logged Critical finding about Refit's double-suffixed paths (not re-reported as a new finding here).
- **Vessel** (120/151) and **Shoreside** (8/8): no shadowing route files exist for these paths at all (only 15 literal `/vessel/...` routes exist repo-wide, and those are almost entirely the already-exempted `/vessel/logbooks/*` set; zero `/shoreside/...` or `/fleet/...` routes exist). These are genuinely, currently showing "Coming Soon" for the large majority of their leaves.
Impact: (a) For Phase 4 prioritization: the real content gaps needing attention are **Vessel** (~120 sub-pages across Crew/Safety/Certificates/Technical/Charter/Accounting/Departments) and all of **Shoreside** (8 items, which read as unbuilt links to sibling-company services: Embrace, Lungfish, Bonefish, InkWELL, MedINK, Crew Concierge, Cosmic Frontier Labs, Dark Ocean) — Refit is already tracked separately in Phase 1. Health, HRIS and New Build do **not** need new pages built; they need their sitemap metadata corrected. (b) Separately, the Health/HRIS/New Build situation is a live fragility risk: it depends entirely on `{healthRoutes}`/`{hrisRoutes}`/`{newBuildRoutes}` staying textually before `{PLACEHOLDER_LEAVES.map(...)}` in `routes/index.tsx`. Any future refactor that reorders that file, switches to `createBrowserRouter`'s object-route API (which ranks differently), or splits `<Routes>` into nested route trees would silently regress all ~95 of these leaves to "Coming Soon" with no test catching it — `src/test/config/sitemapTargets.test.ts` (per Phase 1) only checks leaves carrying an explicit `existing:` field, and none of these do.
Suggested fix: Add `existing:` overrides for the Health, HRIS and New Build leaves in `src/config/sitemap.ts` (pointing at their real, already-correct paths) so they're excluded from `PLACEHOLDER_LEAVES` on the metadata level instead of merely being shadowed by declaration order, and extend `sitemapTargets.test.ts` to assert that no `PLACEHOLDER_LEAVES` path collides with a path any module's own `routes.tsx` declares (this closes the same test gap Phase 1 already identified for Refit, for the other three modules at once).

## Positive baseline notes (for context, not findings)

- Loading skeletons + a distinct, styled empty state (icon + heading + helper text, sometimes a CTA) are used consistently and well across every module sampled except for the missing error-state branch noted above (Vessels, Incidents, Documents, Crew Roster, HRIS Disciplinary/Onboarding overviews all follow the same good pattern).
- `DashboardLayout`/`SidebarNavigation` (the app shell) has solid, deliberate mobile handling: an off-canvas drawer, backdrop overlay, focus management on open/close, Escape-to-close, and a `lg:` breakpoint split between mobile drawer and desktop static sidebar — this is not part of the responsive-behavior finding above, which is about page *content*, not the shell.
- Archive/restore actions (as opposed to delete) are correctly treated as low-risk/reversible and fire without a confirmation dialog (e.g. `TemplatesPanel.tsx` in HRIS onboarding) — this is the right call, not an inconsistency.
