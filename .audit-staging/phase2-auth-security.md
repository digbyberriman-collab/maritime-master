# STORM — Phase 2: Authentication & Session-Security Deep Dive

Scope: `src/modules/auth/**`, `src/lib/api/hooks/useUsersApi.ts`, `supabase/functions/accept-invitation`, `supabase/functions/send-invitation`, `supabase/functions/bulk-invite`, `supabase/functions/admin-actions`, plus targeted greps across `src/` for secrets and XSS surface. Read-only; nothing on disk was modified. Findings below are new/deeper than Phase 1's RBAC-matrix-level coverage — Phase 1's already-reported items (sign-submission PIN no-op, inbound-webhook dead HMAC, hr-daily-sweeper/ais-refresh/idea-sync non-constant-time secret compare, the general 4-overlapping-role-systems ambiguity) are **not** repeated here.

### [AUTH] — Admin-action PIN "step-up" confirmation is never checked server-side; it gates nothing
Severity: Critical
Location: `supabase/functions/admin-actions/index.ts:232-480` (the `reset_account`, `toggle_access`, `reallocate_vessel` cases); client side `src/modules/auth/hooks/useAdminActions.ts:18-39, 101-215`
Description: `admin-actions` implements `set_pin` and `verify_pin` as two of five `action` values. `verify_pin` is sound in isolation (PBKDF2 check, 5-attempt lockout) and, on success, returns a `confirmedUntil` timestamp. But nothing server-side ever *records or checks* that a PIN was verified before the *other* three actions run. `reset_account`, `toggle_access` and `reallocate_vessel` each only check (a) the bearer JWT is valid, and (b) the caller has `user_roles` `dpa`/`superadmin` or legacy `profiles.role` `dpa`/`shore_management`/`superadmin` (lines 82-106). They never read `admin_pins.last_confirmed_at` or accept/verify any PIN-derived proof in the request body. The "confirmation window" (`confirmedUntil`, `CONFIRMATION_WINDOW_MS = 10 * 60 * 1000`) lives *only* in the browser's `sessionStorage` (`useAdminActions.ts:23-39`), and `AdminPinModal.tsx` auto-proceeds (`onConfirmed()`) whenever that client-side flag says so. Calling the edge function directly (curl/devtools/a modified client) with a valid admin session token, with no PIN ever entered, executes every privileged action immediately.
Impact: Any account holding `dpa`/`superadmin` (via `user_roles`) or the legacy `profiles.role` value `dpa`/`shore_management`/`superadmin` can, with a single unauthenticated-by-PIN HTTP call: (1) force-send a password-reset link or invalidate all sessions for any other user in the company, including other admins, (2) disable (and force sign-out) or re-enable any account in the company, or (3) reassign any crew member to any vessel — all with zero PIN input, at any time, from any client. The PIN mechanism gives operators a false sense of a step-up control that does not exist; it is effectively decorative except for the `set_pin`/`verify_pin` actions themselves.
Suggested fix: In `admin-actions/index.ts`, before executing `reset_account`, `toggle_access`, or `reallocate_vessel`, look up `admin_pins.last_confirmed_at` for `userId` and reject (403) unless it is within the confirmation window (e.g. 10 minutes), mirroring the window the client already assumes exists. Alternatively, require callers to pass a short-lived server-issued confirmation token returned by `verify_pin` and validate it on every subsequent privileged call, rather than trusting client-side `sessionStorage` state.

### [AUTH] — Admin PIN comparison is not constant-time
Severity: Low
Location: `supabase/functions/admin-actions/index.ts:29-42` (`verifyPin`)
Description: `verifyPin` derives the PBKDF2 hash of the submitted PIN and compares it to the stored value with plain JavaScript `${saltHex}:${hashHex}' === stored`, which short-circuits on the first mismatched character. This is a timing side-channel on the derived hash (not the raw PIN), and the checklist specifically asked whether this comparison is constant-time — it is not.
Impact: In principle an attacker with very precise network-timing measurement could narrow down the stored hash byte-by-byte; in practice this is very hard to exploit remotely (edge-function/network jitter dwarfs the sub-microsecond timing delta, and comparison is over the hash, not the 6-digit PIN itself), and the existing 5-attempt/15-minute lockout further limits the number of measurable samples available to an attacker. Low real-world exploitability, but worth closing as defense-in-depth.
Suggested fix: Use a constant-time comparison (e.g. Deno's `crypto.subtle` via a manual constant-time byte compare, or `timingSafeEqual` if available in the Deno std/crypto surface) instead of `===`.

### [AUTH] — User enumeration on login and registration
Severity: High
Location: `src/modules/auth/pages/Auth.tsx:159-202`
Description: On login failure, the handler distinguishes two Supabase Auth error strings and shows the visitor a materially different message for each: `"That email and password combination does not match an account…"` for `Invalid login credentials`, versus `"This account has not been confirmed yet. Check your inbox…"` for `Email not confirmed` (lines 162-167). Supabase Auth only returns `Email not confirmed` when the email *does* correspond to a real, unconfirmed account — so this UI reliably tells a visitor whether a given email is registered. Separately, on registration failure the raw Supabase error (`error.message`) is shown verbatim in a toast (lines 190-195), and `auth.signUp` itself is queried and will return an "already registered" style error for existing emails, before any of the (already-broken, see next finding) company/profile logic runs.
Impact: An attacker can enumerate which email addresses belong to real crew/company accounts by (a) submitting a login with any password and reading which of the two distinct messages comes back, or (b) submitting a registration with a candidate email and reading whether it errors as already-registered. This supports targeted phishing and credential-stuffing against confirmed real accounts.
Suggested fix: Return one generic message for all login failures (e.g. "Incorrect email or password, or this account is not yet active — contact your DPA if you believe this is wrong") instead of branching UI copy on the underlying Supabase error string. For registration, use a generic "If this looks wrong, contact your administrator" message rather than surfacing the raw Supabase error text; consider it moot for register once the self-registration flow itself is fixed or fully removed (see next finding).

### [AUTH] — Self-registration ("Create your account") is dead/broken since the Sept-19 signup lockdown, and fails by creating orphaned auth users
Severity: Medium
Location: `src/modules/auth/pages/Auth.tsx:44-52, 141-149, 181-202, 422-438`; `src/modules/auth/contexts/AuthContext.tsx:371-412`; `supabase/migrations/20260919170100_signup_backstop.sql`
Description: The Sept 19 migration correctly closed a privilege-escalation hole by (a) dropping the `authenticated`-role INSERT policy on `companies` entirely, and (b) restricting the profiles self-insert policy to `WITH CHECK (role = 'crew' AND company_id IS NULL)`. However, the client `Auth.tsx` "register" tab and `AuthContext.signUp()` were not updated to match: the form still collects `companyName` and a free-choice `role` (including `dpa`/`shore_management`), and `signUp()` still executes, in order, (1) `supabase.auth.signUp()` — creates a **real Supabase Auth user** — then (2) `INSERT INTO companies` — now unconditionally rejected by RLS — then (3) `INSERT INTO profiles` with the chosen role/company. Step 1 always succeeds before step 2 fails, so every attempt through this form leaves a confirmed-or-unconfirmed **auth.users row with no matching profile and no company**, and the visitor sees an opaque RLS error via `catch`. The in-app comment at `Auth.tsx:424-425` acknowledges self-registration is meant to be closed, but the UI/flow was never removed or disabled.
Impact: Prospective users hit a confusing failure and cannot self-onboard despite the UI implying they can; each attempt also creates an orphaned Supabase Auth identity with no profile, which (a) is dead-weight/PII the company never asked to store, (b) could re-enter the system oddly if a later migration relaxes the profile-insert policy without accounting for these pre-existing orphans, and (c) means the `company_type`/role selector UI is presented and fully interacted with for a flow that can never actually complete.
Suggested fix: Remove or hard-disable the "register" tab now that self-serve signup is a closed, invitation-only model (the login screen already says as much: "Ask your DPA or fleet administrator for an invitation"), or replace it with a real "request access" flow that doesn't call `auth.signUp` client-side. If any self-serve tier is intended to remain, gate the whole flow behind a working, RLS-consistent server-side endpoint (e.g. an edge function using the service role) instead of three sequential client-side calls that can partially fail.

### [AUTH] — Orphaned invitation-acceptance mechanism remains a live, unauthenticated public endpoint
Severity: Low
Location: `supabase/functions/accept-invitation/index.ts` (whole file); dead client code at `src/lib/api/hooks/useUsersApi.ts:135-222` (`useSendInvitation`, `useBulkInvite`)
Description: The real, currently-used invitation path is Supabase Auth's own `inviteUserByEmail` (via `send-invitation`/`bulk-invite` + `_shared/invite-helpers.ts`), which never touches `profiles.invitation_token`. A second, older mechanism still exists in the codebase: `useSendInvitation`/`useBulkInvite` generate a `crypto.randomUUID()` token and write it directly into `profiles.invitation_token`/`invitation_token_expires` from the browser (no email is ever sent by these hooks — the token is simply written to the DB and never transmitted anywhere), and the `accept-invitation` edge function still accepts `{token, password}` with **no authentication of any kind**, looks the profile up by `invitation_token`, and calls `auth.admin.updateUserById(..., {password})` to set that account's password. Confirmed via repo-wide grep that no component currently imports `useSendInvitation`/`useBulkInvite`, so no live code path populates `invitation_token` today — the endpoint is currently inert in practice, but still deployed and reachable, and `config.toml` sets `verify_jwt = false` for it (correctly, since an unauthenticated invitee needs to reach it — but that also means there is no secondary check at all).
Impact: Low today given the token is never populated by any live path. But it is a landmine: if this hook is ever wired back up (it reads as production-ready, exported API-hooks-style code, easy to reach for by a future developer), or if `invitation_token` is ever set by any other means (manual DB edit, a future migration, an admin tool), the endpoint will accept a password change from an unauthenticated caller who merely knows/guesses the token, with no server-side confirmation it was ever meant to be used, and no rate-limiting on guesses (the token itself is high-entropy so brute force is not practical, but there is no logging/lockout on repeated wrong-token attempts either).
Suggested fix: Delete the dead `useSendInvitation`/`useBulkInvite` hooks and the `accept-invitation` edge function (and its `invitation_token`/`invitation_token_expires` columns) now that the Supabase-Auth-native invite flow is the sole live mechanism, to remove the orphaned attack surface and prevent a future developer from re-wiring it.

### [AUTH] — Invitation/bulk-invite authorization checks the legacy `profiles.role`, not the RBAC root of trust
Severity: Medium
Location: `supabase/functions/send-invitation/index.ts:52-56`; `supabase/functions/bulk-invite/index.ts:50-55`
Description: Both edge functions gate "who may invite new users" on `['dpa','shore_management','master','superadmin'].includes(callerProfile.role)`, reading the legacy `profiles.role` column. Per Phase 1's RBAC findings, `profiles.role` is one of four overlapping, "confirmed still unreconciled" authorization systems, and is not the same source of truth as `user_roles`/`has_role()` (which is what Postgres RLS and `admin-actions` treat as canonical). A DB trigger added in `20260917190000_hris_review_fixes.sql` (`profiles_guard_privileged_columns`) now prevents a non-admin from *self*-elevating `profiles.role` via a direct client update, so the most severe version of this gap (self-service escalation) is closed — but the two systems can still legitimately diverge (e.g. an account whose legacy `role` was set to `master`/`dpa` historically or by an HR admin, while its current `user_roles`/RBAC grants are narrower, or vice versa), and these two edge functions only ever consult the older, weaker field.
Impact: A user whose `profiles.role` says `master`/`dpa` but whose real, current RBAC role/permissions are narrower can still send invitations and bulk-invite (potentially creating new accounts / re-triggering auth invites) in their company, independent of what the "Roles & Permissions" UI shows administrators has been granted. This is a authorization-surface instance of the general reconciliation gap Phase 1 flagged structurally, now pinpointed to two specific edge functions.
Suggested fix: Change both functions to check `has_role(callerId, 'dpa')`/`has_role(callerId, 'superadmin')` (or the RBAC `rbac_company_permission`/`hr_can_admin` helpers already used elsewhere in the codebase) instead of `profiles.role`, consistent with `admin-actions`' `hasNewRoleAccess` check.

### [AUTH] — No application-level rate limiting or lockout on the login form itself
Severity: Medium
Location: `src/modules/auth/contexts/AuthContext.tsx:366-369` (`signIn`); `src/modules/auth/pages/Auth.tsx:159-180`
Description: `signIn` calls `supabase.auth.signInWithPassword` directly with no attempt counter, backoff, CAPTCHA, or client-side throttling of any kind, and there is no wrapper edge function in front of login (unlike the PIN system, which does implement its own 5-attempt lockout). Whatever brute-force protection exists is entirely whatever the Supabase Auth project's own rate-limit configuration provides, which is not expressed anywhere in this repository (`supabase/config.toml` has no `[auth]` rate-limit section) and so cannot be verified as present or adequate from the codebase alone.
Impact: If the Supabase project's dashboard-level auth rate limits are permissive (or were relaxed at some point), credential-stuffing/brute-force against `signInWithPassword` has no additional application-layer backstop.
Suggested fix: Confirm and document the Supabase Auth project's rate-limit settings (Dashboard → Authentication → Rate Limits) as part of the deployment checklist; consider adding an application-level exponential backoff or CAPTCHA (e.g. hCaptcha/Turnstile, which Supabase Auth supports natively) on repeated failed logins from the same client, independent of the platform default.

### [AUTH] — `canAccessModule` fails open for all non-sensitive modules while RBAC permissions are still loading
Severity: Low
Location: `src/modules/auth/contexts/AuthContext.tsx:217-311`, specifically lines 260-262
Description: `canAccessModule` explicitly blocks access (`return false`) for `hris` and `health` while `rbacInitialized`/`rbacLoading`/`practitionerDisciplinesLoaded` are still settling (comment: "must never fail open"). Every other module falls through to `if (!rbacInitialized || rbacLoading) { return true; }` (line 260-262) — i.e. during the window between sign-in and the async `loadPermissions()` RBAC fetch resolving, every module *other than* HRIS/Health is granted access unconditionally, regardless of what the user's eventual RBAC permissions will turn out to be.
Impact: Narrow in practice: Phase 1 already established that only HRIS and Health are route-gated by `ModuleRoute`/`canAccessModule` at all (32 of 34 modules have no route-level gate and rely on `canAccessModule`'s own "allow by default when module not in `MODULE_ACCESS`" fallback anyway — see `AuthContext.tsx:305-310`). So this loading-window fail-open mostly duplicates an already-reported structural gap rather than opening a new one; the residual concern is any *other* future or hidden call site that trusts `canAccessModule` as an actual gate for a sensitive module beyond HRIS/Health, which would inherit this same brief fail-open window.
Suggested fix: Default to `false` (not `true`) while RBAC is loading for every module, matching the pattern already used for HRIS/Health, and show a loading state in the UI rather than transiently granting access.

### [AUTH] — Cosmetic hardcoded-looking API key in a mock settings screen
Severity: Cosmetic
Location: `src/modules/settings/pages/APIIntegrations.tsx:1023-1031`
Description: A "Configuration" tab renders `<Input type="password" value="sk_live_123456789abcdef" />` as a static, non-stateful value (not backed by `useState`/an API call) — this is a UI mockup for a settings page, not a live credential, and the endpoint (`https://services.marinetraffic.com/api`) beside it is likewise a static placeholder.
Impact: None functionally (not a real secret, not wired to any request), but the literal string is shaped exactly like a real live Stripe-style secret key, which could trip up automated secret scanners or mislead a future engineer into thinking a real key was ever placed here.
Suggested fix: Replace with an obviously-fake placeholder (e.g. `"sk_live_••••••••••••"` or `"<your-api-key>"`) so it reads unambiguously as a UI mock rather than a leaked credential.

## Items checked with no material finding

- **Custom session-refresh races**: `AuthContext.tsx` adds no custom token-refresh logic beyond Supabase's built-in `autoRefreshToken: true`. The only custom timing logic is a 5-second safety timer that forces `loading = false` if `getSession()` hangs (`AuthContext.tsx:354-358`) — this fails *closed* (worst case, a slow network briefly renders the logged-out state), not open.
- **PIN hashing algorithm** (`admin-actions/index.ts:14-27`): PBKDF2-SHA256, 100k iterations, random 16-byte salt per user — a sound choice for a 6-digit PIN, and lockout after 5 failed attempts (15 minutes) is implemented and correctly ordered (lock-check happens before the PBKDF2 derivation on each attempt).
- **Other PIN re-implementations**: no other code path re-implements PIN hashing/verification; the only other PIN-shaped check (`sign-submission`) was already flagged by Phase 1 as a no-op and is not re-analyzed here per instructions.
- **XSS via Legal module Markdown / ISM forms**: the Legal document editor/viewer is a hand-written Markdown-to-AST-to-React renderer with no HTML injection anywhere and href-scheme whitelisting on links; ISM form rendering has zero `dangerouslySetInnerHTML`/`innerHTML` usages.
- **Password-reset enumeration**: `resetPasswordForEmail` + the app's generic "Email sent" toast do not distinguish existing vs. non-existing emails.
