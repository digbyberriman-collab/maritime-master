# Phase 2 — Forms & Validation Audit

Scope: `src/modules/**` client-side forms/wizards, cross-referenced against `supabase/migrations/**` for server-side (DB/RLS) enforcement. Read-only; no files modified except this report. Companion to `SITE_MAP.md` and the four `phase1-*.md` reports.

Method: grepped for `react-hook-form` / `zod` / `yup` / manual `onSubmit` / `.insert(`/`.update(`/`.rpc(` across all 34 modules to map validation-library adoption, then deep-read 6+ representative forms (Legal `IntakeWizard`, ISM `CreateTemplate` form builder, Incidents `ReportIncidentModal`, HRIS `ContractFormDialog`, Crew `CrewFormModal`, New Build `Decisions`/`Areas`/`Suppliers`) plus every file-upload flow found, comparing each against its target table's migration for NOT NULL / CHECK / RLS parity.

### [FORMS] — New Build entity-creation forms write to tables with no RLS tenant scoping at all
Severity: Critical
Location: `supabase/migrations/20260617180527_0e712de7-236b-4177-8c56-faf978050287.sql:32,49,64,97,117,138,164,183,198,214,230,249,264,279,298,320,337,356,376,398,420,441,456,472,490,504,532,546,559,579,599,615,630,646,663,679,694,715,734,752,771,791` (43 `CREATE POLICY "nb_*_auth_all" ON public.nb_* FOR ALL TO authenticated USING (true) WITH CHECK (true)` statements); forms that write through these policies include `src/modules/new-build/pages/Decisions.tsx:79-102` (RAID/decisions), `src/modules/new-build/pages/Areas.tsx:127-152`, `src/modules/new-build/pages/Suppliers.tsx:274-313`, and every other New Build page (Files, Phases, equipment, purchase orders, drawings, materials, etc.)
Description: Every one of the 43 `nb_*` tables underlying the entire New Build module (areas, suppliers, decisions/RAID, files, milestones, change orders, equipment, purchase orders, drawings, materials, RASCI assignments, contacts, etc.) was created with the literal policy `USING (true) WITH CHECK (true)` for all authenticated users — i.e., no company/tenant scoping whatsoever at the row level. Compounding this, every one of these tables' `company_id` column is declared `NOT NULL DEFAULT '00000000-0000-0000-0000-000000000000'::uuid` (e.g. `nb_decisions`, `nb_areas`, `nb_suppliers` — see the same migration, lines 44/59), and none of the client insert payloads (`Decisions.tsx:79-93`, `Areas.tsx`, `Suppliers.tsx`) ever set `company_id` — they only set `project_id`/`created_by`. So every New Build row in every tenant's database is written with the same dummy all-zero `company_id`, and the RLS policy doesn't check it anyway. A later migration (`20260919200000_nb_search_and_buckets.sql:206-215,222-238`) added a `nb_project_in_company()` helper and used it to properly scope the *storage buckets* for drawings/deck-plans/material-swatches/yard-standards, but never went back and applied the same fix to the 43 underlying **tables** — so the file blobs are now tenant-scoped but the database rows describing them (titles, suppliers, decisions, RAID items, milestones, equipment, POs) are not.
Impact: Any authenticated user of any company on the platform can read, insert, update or delete any other company's entire New Build project data (RAID log entries, supplier relationships, decisions, change orders, purchase orders, equipment lists, milestones) — a full cross-tenant confidentiality and integrity breach for the whole module, reachable simply by knowing (or enumerating) another company's `project_id`. This is the same class of bug already flagged Critical in Phase 1 for `crew_import`, but far larger in blast radius (43 tables vs. 1). New Build also has no module-level RBAC gate per Phase 1 §"Medium — Refit and New Build modules carry no RBAC/module-level access gate," so there isn't even an app-layer speed bump.
Suggested fix: Replace all 43 `*_auth_all` policies with policies gated by `public.nb_project_in_company(project_id)` (mirroring the pattern already used for the storage buckets), backfill the real `company_id` on every existing row from its `project_id → nb_projects.company_id`, drop the dummy-UUID default, and add `company_id` to every client insert payload as defense in depth even after RLS is fixed.

### [FORMS] — Incident and crew-travel-document uploads have no server-side file type/size enforcement, and one has no tenant scoping either
Severity: Critical
Location: `supabase/migrations/20260125220549_d85c9e1e-a6aa-413c-a0a5-09dafd5a0c67.sql:147,150-160` (bucket `incident-attachments`); `src/modules/incidents/hooks/useIncidents.ts:403-432` (`useUploadIncidentAttachment`); `supabase/migrations/20260129131533_33529d78-d422-4f59-94ea-055eebe46507.sql:479-499` and its fix in `supabase/migrations/20260610104821_59b24a7f-182c-487c-afc5-327610bf9dfd.sql:33-72` (bucket `crew-travel-documents`); `src/modules/crew/pages/admin/DocumentUploadPage.tsx:90-96,209-216`
Description: The `incident-attachments` bucket was created with only `(id, name, public)` — no `file_size_limit`/`allowed_mime_types` columns set — and its storage policies are `bucket_id = 'incident-attachments' AND auth.role() = 'authenticated'` with **no company/tenant scoping at all** (unlike the sibling `documents` bucket, which correctly checks `(storage.foldername(name))[1] = p.company_id::text`). This was never fixed in any later migration. `useUploadIncidentAttachment` (`useIncidents.ts:406-423`) uploads whatever `File` object it receives, with zero server-side validation of type or size — the only gate is the client's `react-dropzone` `accept`/`maxSize` props in `ReportIncidentModal.tsx:141-148`, which a direct Storage API call (bypassing the UI) trivially skips. The `crew-travel-documents` bucket has the same gap (no `file_size_limit`/`allowed_mime_types` ever set, in either its original or its June 2026 tenant-scoping-fix migration), and its own upload page (`DocumentUploadPage.tsx`) doesn't even set a client-side `maxSize` (compare to the incident modal's 10 MB), so an arbitrarily large file of any MIME type can be pushed into it via the UI already, let alone via direct API.
Impact: (1) Any authenticated user of **any tenant** can read every other tenant's incident-evidence photos/videos/documents from `incident-attachments` (cross-tenant confidentiality leak on what is often the most sensitive evidence in the platform — injury photos, near-miss documentation). (2) Both buckets accept arbitrary file types/sizes server-side, so a user (or a compromised/malicious client) can upload executables, HTML/SVG with embedded scripts, or oversized files disguised with an image/PDF extension; if these URLs are ever served back with an inferred content-type or opened by another user's browser, this is a stored-content/XSS and storage-abuse vector, not just a validation gap.
Suggested fix: Add `file_size_limit` and `allowed_mime_types` (image/pdf/doc types only, matching the client `accept` lists) to both buckets at the bucket-config level (as already done correctly for `avatars`, `documents`, `legal-attachments`, and the `nb_*` file buckets), and rewrite the `incident-attachments` storage policies to scope by company (e.g. via a `company_id` path-prefix check joined through `incidents.company_id`, as `legal-attachments` does with `legal_attachment_path_allowed()`).

### [FORMS] — ISM Form Template Builder wizard has no per-step (or even per-field) validation; "Next" is never gated
Severity: High
Location: `src/modules/ism/forms/pages/CreateTemplate.tsx:442-446` (`nextStep` — unconditional), contrast with `src/modules/incidents/components/ReportIncidentModal.tsx:203-226,933` (`isStepValid()` gating `disabled={!isStepValid()}`); DB: `supabase/migrations/20260127210031_20df2870-be0e-4094-8c28-d091d00957dd.sql:36-101` (`form_templates` table — `form_type`/`status`/`initiation_mode` are plain `VARCHAR` with no `CHECK`)
Description: Unlike the Incident report modal (which disables "Next" via `isStepValid()` per step) and the Legal `IntakeWizard` (which calls `validateIntakeStep`/`validateIntake` with a zod schema before advancing or submitting), the ISM form-template builder's `nextStep()` (`CreateTemplate.tsx:442-446`) has **no validity check at all** — a user can click through Upload → AI Extraction → Edit Fields → Configure → Review with every field blank. The *only* validation anywhere in the 5-step flow is at the very end, in `saveTemplate()` (`CreateTemplate.tsx:380-387`), which checks just `template_code` and `template_name` are non-empty — nothing validates that `form_schema.fields` is non-empty, that `required_signers` entries have a `role` selected, or that `form_type`/`status`/`initiation_mode`/`signature_type` are one of the intended enum values. The DB mirrors this: `form_templates.form_type`, `.status`, `.initiation_mode` are all plain `VARCHAR` with **no `CHECK` constraint**, so a direct API insert (or a future UI bug) can silently store a `form_type` outside the 9 values the UI presents, or `status = 'PUBLISHED'` with an empty `form_schema.fields` array — a live, signable ISM form with zero fields.
Impact: A DPA/admin can accidentally publish a completely empty or nonsensical ISM form template (no fields, no required signers) fleet-wide, and nothing — client or server — stops it. Because this is a compliance/audit-trail feature (ISM forms drive incident/NC/CAPA workflows per `can_trigger_incident`/`can_trigger_nc`/`can_trigger_capa` columns), a malformed published template silently degrades the safety-management-system paper trail.
Suggested fix: Gate each step's "Next" button on a per-step validity check (mirroring `ReportIncidentModal`'s `isStepValid()` pattern), require at least one field before allowing "Configure"/"Review", and add `CHECK` constraints on `form_type`, `status`, and `initiation_mode` matching the client-side enum lists; consider a DB constraint or trigger disallowing `status = 'PUBLISHED'` when `jsonb_array_length(form_schema->'fields') = 0`.

### [FORMS] — ISM form-builder "Upload Source Document" fails silently due to a client/RLS path mismatch
Severity: Medium
Location: `src/modules/ism/forms/pages/CreateTemplate.tsx:159-187` (path `form-templates/${Date.now()}.${fileExt}`); RLS: `supabase/migrations/20260125163105_1d769302-27a6-4c6b-8037-e5d0bff0caa4.sql:181-192` (`documents` bucket INSERT policy requires `(storage.foldername(name))[1] = p.company_id::text`)
Description: `handleFileUpload` uploads the source PDF/DOCX to the `documents` bucket at `form-templates/<timestamp>.<ext>` — but every storage policy on that bucket requires the **first path segment to equal the uploader's `company_id`** (`documents` bucket policies, all four CRUD policies use the same `(storage.foldername(name))[1] = p.company_id::text` check). Since `"form-templates"` never equals a company UUID, this upload's RLS `WITH CHECK` should fail on every real call. The code only branches on success (`CreateTemplate.tsx:167: if (!uploadError) { ...populate source_file_url... }`) — there is no `else`/error branch, no toast, nothing shown to the user. The step just silently proceeds without a populated `source_file_url`, and the subsequent "AI Extraction" step (which reads `templateData.source_file_url`) has nothing to extract from.
Impact: The advertised "upload a PDF and let AI extract the fields" flow is silently broken for every real user under RLS (works only against a service-role/dev bypass), and the failure is invisible — no error toast, no console-visible-to-the-user message — so the person building the template has no idea why extraction returned nothing.
Suggested fix: Prefix the upload path with the user's `company_id` (e.g. `${profile.company_id}/form-templates/${Date.now()}.${fileExt}`, matching every other bucket's convention in this codebase) and surface `uploadError` to the user via toast instead of silently swallowing it.

### [FORMS] — Leave-request date-range validation exists in one submission path but not the other, for the same table
Severity: Medium
Location: `src/modules/crew/pages/LeaveRequestsPage.tsx:187-193` (admin-facing: checks `if (form.end_date < form.start_date)`); `src/modules/crew/pages/LeaveManagement.tsx:122-137` (crew self-service: `handleSubmitRequest` — no such check); DB: `supabase/migrations/20260127170858_dad2e300-898a-443f-8d06-9cf52661e175.sql:297-312` (`leave_requests` table — `start_date`/`end_date` are `NOT NULL` with **no `CHECK`** relating them)
Description: The same business rule — a leave request's `end_date` must not be before its `start_date` — is implemented in `LeaveRequestsPage.tsx` (the admin/purser leave-management screen) but is **completely absent** from `LeaveManagement.tsx` (the crew member's own self-service leave-request form), which only checks that the fields are non-empty (`!newRequest.leave_type || !newRequest.start_date || !newRequest.end_date`, line 124) before inserting straight into `leave_requests`. The database table has no `CHECK (end_date >= start_date)` constraint to catch what the client misses.
Impact: A crew member using the self-service form can submit (and have auto-recorded) a leave request with an inverted date range (e.g., end date before start date). This silently corrupts every downstream calculation that assumes a non-negative range — `differenceInDays(end, start) + 1` (used for day-count displays in both `LeaveRequestsPage.tsx:448,545` and `LeaveManagement.tsx:414`) returns a nonsensical negative-then-incremented value, and the admin-side overlap detector (`overlapsAny`) may behave unpredictably against an inverted range it was never designed to see.
Suggested fix: Extract the date-range check into one shared helper (there is already a good precedent for this in `src/modules/hris/lib/contractHelpers.ts`'s `validateContractDates`) and call it from both `LeaveManagement.tsx` and `LeaveRequestsPage.tsx`; additionally add `CHECK (end_date >= start_date)` on `leave_requests` server-side so any other/future entry point (imports, RPCs, direct API calls) can't create an inverted range either.

### [FORMS] — Validation-library adoption is inconsistent across modules; only 2 of 34 modules use react-hook-form + zod
Severity: Low
Location: repo-wide; `react-hook-form` appears in 27 files (21 in `hris`, 4 in `crew`, 1 each in `vessels`/`emergency`); `zod` in 22 files (13 `hris`, 4 `crew`, 2 `auth`, 1 each `vessels`/`settings`/`legal`); modules with real forms but **no** validation library at all include `ism` (`src/modules/ism/forms/pages/CreateTemplate.tsx`), `new-build` (`src/modules/new-build/pages/*.tsx`), `incidents` (`src/modules/incidents/components/ReportIncidentModal.tsx`), `refit`, `maintenance`, `logbooks`, `itinerary`, `risk-assessments`, `drills`, `development`, `audits`, `training`, `documents`, `certificates`
Description: `hris` and (to a lesser degree) `crew` have converged on `react-hook-form` + `zodResolver` + the shared shadcn `<Form>` primitives, giving those forms consistent inline field errors, schema-driven cross-field rules, and a single source of truth for validity. The other ~28 modules use ad hoc `useState` + manual `if (!field) toast.error(...)` checks (or, in the New Build pages, bare HTML5 `required` attributes with no JS-level check at all — see `Areas.tsx:130`, `Suppliers.tsx:278`). This is not inherently wrong, but it means validation quality and thoroughness vary widely by whichever pattern the module's original author happened to use, with no shared cross-field-validation helper reused between modules (each wizard/dialog reinvents its own date-range check, its own "is this step complete" logic, etc. — see the two date-range and two step-gating findings above).
Impact: No single security hole, but it means fixing a validation gap in one module (e.g., adding a shared date-range validator, or a shared "step complete" gate) doesn't propagate anywhere else, and it will keep costing the same class of bug (missing cross-field check, ungated wizard step) each time a new form is added by a different author. It also means future audits/reviews have to re-derive validation completeness form-by-form rather than trusting one shared layer.
Suggested fix: Standardize new/rewritten forms on the `react-hook-form` + `zod` + shadcn `<Form>` pattern already established in `hris`, extract the cross-field helpers that already exist there (`contractHelpers.ts`'s date-range validator is a good template) into a shared `src/shared/lib/validation` module other feature modules can import instead of re-deriving.

### [FORMS] — Client/server validation parity is good where storage buckets were set up with `file_size_limit`/`allowed_mime_types`, uneven elsewhere (contrast, not a new bug)
Severity: Cosmetic
Location: Good examples — `avatars` bucket: `supabase/migrations/20260917110500_hris_avatars_bucket.sql:4-6` (server) matches `src/modules/hris/lib/profileForm.ts:203-214` (`validateAvatarFile`, client) exactly on MIME list and 5 MB limit; `crew_contracts` table: `supabase/migrations/20260917110000_hris_phase1_employee_records.sql:87-124` (`CHECK` on `contract_type`, `status`, `wage_frequency`, and `end_date >= start_date`) matches `src/modules/hris/lib/contractHelpers.ts:157-204` (`contractFormSchema`) field-for-field. Weaker examples — `legal_requests.currency`/`.contract_value`: client (`src/modules/legal/lib/requests.ts:194-200`) requires a 3-letter currency code and a non-negative numeric value, but the DB (`supabase/migrations/20260919120000_legal_module.sql:160-161`) has no matching `CHECK`; `form_templates.form_type`/`.status` (see finding above) has none either.
Description: This is included as a positive contrast to the Critical/High findings above: the codebase clearly *knows how* to do defense-in-depth correctly (avatars and HRIS contracts are textbook examples — the DB `CHECK`s are a literal mirror of the zod schema), which makes the gaps in New Build, ISM templates, incident attachments and legal currency/value fields look more like inconsistent follow-through across modules/authors than a systemic lack of awareness.
Impact: None by itself; flagged so Phase 3 prioritization can note that the fix pattern to replicate already exists in-repo (HRIS/avatars) rather than needing to be invented.
Suggested fix: When remediating the Critical/High items above, use `crew_contracts` and the `avatars` bucket as the reference implementation for "what done looks like" in this codebase.

## Answers to the checklist's specific questions

1. **Validation library consistency**: Mixed. `react-hook-form` + `zod` is the dominant, best-practice pattern but only in `hris` (21/27 files) and partially `crew` (4 files); `auth` and `settings` use zod without react-hook-form for a couple of forms; the other ~28 modules (including the high-traffic ISM forms module, all of New Build/Refit, Incidents, Maintenance, Logbooks, Itinerary) use manual `useState` + ad hoc `if` checks or bare HTML5 `required`, with no shared validation library at all.
2. **Client/server parity** (6 forms checked): Legal `IntakeWizard` — good (zod schema, DB `CHECK`s on `request_type`/`priority`/`status`, minor gap on currency/value). HRIS `ContractFormDialog` — best-in-repo (DB `CHECK`s mirror zod exactly, including cross-field date rule). Incident `ReportIncidentModal` — partial (severity range and enums enforced server-side; the description's 50-character minimum, and the severity→investigation_required/dpa_notified business rules, are client-only). ISM `CreateTemplate` (form builder) — weak (no per-step gating; DB has no enum `CHECK`s at all for `form_type`/`status`/`initiation_mode`). Crew `CrewFormModal` — good field-level zod, but its pre-submit "email already exists" check is a client-side TOCTOU race (the real uniqueness guarantee is Supabase Auth's own `createUser` rejecting the edge-function call). New Build `Decisions`/`Areas`/`Suppliers` — worst case: essentially **no server-side enforcement at all**, since RLS on all 43 underlying tables is `USING (true) WITH CHECK (true)` — a direct API call bypassing the UI can insert/update/delete any tenant's data with anything that satisfies a bare `NOT NULL`.
3. **File upload validation**: Uneven. Well done (client + matching server `file_size_limit`/`allowed_mime_types`, plus company-scoped storage RLS): `avatars`, `documents`, `legal-attachments`, and the New Build `nb_regulations`/`nb-deck-plans`/`nb-material-swatches`/`nb-yard-standards` buckets. Not done at all server-side (client `react-dropzone` `accept`/`maxSize` is the *only* gate, trivially bypassed via direct Storage API calls): `incident-attachments` (also missing tenant scoping — cross-tenant read) and `crew-travel-documents` (tenant scoping was fixed in June 2026, but MIME/size limits were never added). `development-documents` has a SELECT policy scoped only to "any authenticated user," not to company. No path in the app currently allow-lists executable/script MIME types by mistake, but the two buckets above allow-list *nothing*, which is equivalent in practice.
4. **Duplicate/conflicting validation logic**: The clearest example is the leave-request date-range rule (`end_date >= start_date`), implemented in `LeaveRequestsPage.tsx` but missing entirely from `LeaveManagement.tsx`'s crew self-service form, with no DB `CHECK` as a backstop. Email-format validation (zod's built-in `.email()`) is, by contrast, consistently applied in all 4 places it appears (`CrewFormModal`, `NextOfKinFormDialog`, `recruitment.ts`, `Auth.tsx`) with no drift. The ISM form-type/status enums are defined once in the UI's `FORM_TYPES`/status literals but never mirrored as a DB `CHECK`, so there's a single source of truth today but nothing stopping it from drifting silently if the DB is ever written to from a second place.
5. **Multi-step wizard state**: All three wizards found (Legal `IntakeWizard`, Incidents `ReportIncidentModal`, ISM `CreateTemplate`) keep their step index in component `useState`, not in the URL/route — so the specific "skip ahead via URL manipulation" vector does not apply to any of them; there is no route param or query string encoding wizard step. Within-component gating quality still varies: `IntakeWizard` and `ReportIncidentModal` both validate the current step before allowing "Next"/"Continue" (`validateIntakeStep` / `isStepValid()`); `CreateTemplate`'s `nextStep()` has no such gate at all (see High finding above), and only validates two fields at the very final Save/Publish action.
